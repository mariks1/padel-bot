# Контекст для сайта и интеграции с Padel Americano Bot

Срез локального кода на 24 сентября 2026 года. Документ можно целиком передать разработчику сайта или его кодинг-агенту. Сведения о работающем сервере и адресе продакшена здесь не подтверждены: описан репозиторий.

## Короткий ответ на «какая апишка у ботика?»

Публичного HTTP API пока нет. Бот написан на TypeScript, работает через grammY и Telegram long polling, хранит данные в SQLite. Бизнес-операции доступны через внутренний `TournamentService`: игроки, создание турнира, расписание, запись/исправление счёта, отмена, статистика и рейтинг.

Чтобы сайт и бот показывали одни данные, предлагаем общий backend на основе этого сервиса и одну основную базу. Сайт обращается к HTTP API, бот — к тому же сервису внутри backend либо к его API. Генерация расписания и расчёт статистики должны выполняться в одном месте. HTTP-маршруты ниже — предложение для реализации, сейчас вызывать их нельзя.

## Что уже умеет продукт

- Сохранять игроков: гостя по имени, игрока с `@username` или себя с Telegram-привязкой. Одинаковые имена разрешены.
- Создавать Americano из сохранённых игроков, выбирать корты и сумму очков за матч.
- Генерировать всё расписание сразу: пары, соперников, раунды, корты, отдыхающих.
- Вводить счёт по матчам текущего раунда; после заполнения раунда переходить к следующему.
- Показывать текущую таблицу турнира, историю турниров и матчи каждого раунда.
- Исправлять результаты через историю, в том числе после завершения турнира.
- Отменять турнир с подтверждением: история остаётся, результаты перестают влиять на общую статистику.
- Показывать общий рейтинг, личную статистику и двух лучших партнёров по разным показателям.
- Искать статистику по имени, части имени или `@username`; менять своё имя через `/name`.

Отдельные функции бота: `/all` для пинга беседы и `/egor` для общего счётчика ошибок. Для турнирного сайта они не обязательны.

В текущем коде нет регистрации на будущие события, бронирования кортов, платежей, клубов, ролей организаторов, Elo, удаления игроков, снятия результата матча, восстановления отменённого турнира или редактирования состава уже созданного турнира. Такие функции потребуют отдельного согласования модели.

```bash

npm test

```

`npm run build` выполняет только `tsc --noEmit`, а не создаёт `dist`. `npm start` печатает демонстрационное расписание и не запускает ни бота, ни HTTP-сервер. `npm run bot` читает `.env`; требуется `TELEGRAM_BOT_TOKEN`.

Путь к базе задаётся через `PADEL_DATABASE_PATH`, по умолчанию `data/padel.sqlite`. В Compose это `/app/data/padel.sqlite` в volume `padel-data`; HTTP-порты не опубликованы. Токен Telegram остаётся на сервере и не используется как ключ доступа сайта. `.env`, рабочую базу и логи не нужно передавать вместе с этим документом.

## Сущности и идентификаторы

Ниже текущие типы с заменой `Date` на строку для JSON. Это описание данных, а не уже существующий сетевой контракт.

```ts
interface Player {
  id: string;
  name: string;
  telegramUserId?: number;
  telegramUsername?: string;
}

type Team = readonly [Player, Player];

interface Match {
  id: string;
  court: number;
  team1: Team;
  team2: Team;
  pointsToPlay: number;
  team1Score?: number;
  team2Score?: number;
  excludedFromStandingsPlayerIds?: readonly string[];
}

interface Round {
  number: number;
  matches: readonly Match[];
  restingPlayers: readonly Player[];
}

interface Tournament {
  id: string;
  name: string;
  players: readonly Player[];
  courts: number;
  pointsPerMatch: number;
  rounds: readonly Round[];
  createdAt: string; // ISO 8601; внутри приложения Date
  cancelled?: boolean;
}
```

- `player.id` — основной идентификатор игрока; сервис создаёт UUID. Не связывать записи по имени или username.
- `tournament.id` по умолчанию UUID, но внутренний генератор допускает переданный ID. Для клиентов ID лучше считать непрозрачной строкой.
- `match.id` имеет вид `r1-c1` и уникален только внутри турнира. Полный ключ — `(tournamentId, matchId)`.
- Номера раундов и кортов начинаются с 1. Количество заявленных кортов может быть больше фактически используемого.
- Команды и отдыхающие содержат полные объекты игроков, а не только ID: это сохранённые копии. Актуальную Telegram-привязку следует брать из реестра игроков.
- `telegramUsername` в UI сохраняется без `@`; username сравнивается без учёта регистра. Сам сервис не является полноценным валидатором произвольного HTTP-ввода.
- Отсутствующий счёт означает «не введён». Ноль — валидное число очков. При JSON-сериализации `undefined` пропадает; `null` сейчас не предусмотрен типом счёта.
- `cancelled` у старых турниров может отсутствовать: это означает, что турнир не отменён.
- `createdAt` — момент создания, отдельной даты запланированной игры нет.

`TournamentInput` сейчас принимает `{ id?, name?, players: Player[], courts, pointsPerMatch }`. Для будущего HTTP API предлагаем принимать `playerIds` и разрешать их на сервере через реестр игроков: клиент не должен присылать произвольные копии профилей.

## Правила, которые должны совпадать

### Создание и расписание

Генератор проверяет: минимум 4 игрока, уникальные ID, непустые имена, положительные целые `courts` и `pointsPerMatch`. В Telegram UI доступны 1–4 корта и 16/24/32 очка. Сам генератор этими вариантами не ограничен; предельный размер турнира для публичного API ещё предстоит задать.

Состав пар не зависит от результатов матчей. Результат генерации сохраняется целиком; уже сохранённый турнир не пересчитывается после обновления алгоритма.

| Состав | Текущее поведение |
| --- | --- |
| 4, 8, 12, 16 игроков | Circle Method: каждому по `N − 1` матчей, каждый с каждым в партнёрах один раз; матчи упаковываются по доступным кортам |
| 12 игроков, 2 корта | 33 матча: 16 полных раундов и 1 матч в 17-м; каждому 11 матчей |
| 11 игроков, от 2 кортов | 11 раундов по 2 матча; каждому 8 матчей с разными партнёрами и 3 отдыха, без двух отдыхов подряд |
| Прочие составы с отдыхом | `N` раундов, каждому `4 × min(courts, floor(N / 4))` матчей |
| Прочие составы без отдыха | `N − 1` раундов |

Равное количество матчей важнее заполнения всех кортов. Повторы соперников минимизируются, но их полное отсутствие не гарантируется. Для общего алгоритма нельзя обещать отсутствие повторов партнёров. Сайт должен отображать возвращённое расписание и `restingPlayers`, а не восстанавливать их собственной формулой. Порядок входных игроков и их ID также могут влиять на подбор.

### Счёт, завершение и отмена

- Оба счёта — неотрицательные целые, сумма строго равна `match.pointsToPlay`. При 32 очках допустимы `20:12`, `16:16`, `0:32`; `6:4` недопустим. Это сумма очков матча, а не число очков до победы.
- Очки команды целиком начисляются каждому её игроку. При `20:12` оба победителя получают по 20 набранных и 12 пропущенных очков.
- Матч сыгран, когда присутствуют оба счёта. Раунд завершён, когда сыграны все его матчи; турнир — когда сыграны все матчи.
- Сохранённого поля `status`, текущего раунда или указателя текущего турнира нет. В SQLite история выдаётся по `created_at DESC`; бот выбирает первый неотменённый турнир с несыгранными матчами. Несколько незавершённых турниров допускаются.
- Обычная кнопка ввода защищена от повторного сохранения уже сыгранного матча. Через историю результат можно изменить. Сам `recordScore` записывает и перезаписывает результат, не различая эти два сценария.
- `cancel` выставляет `cancelled: true` и идемпотентен. Отмена возможна и для завершённого турнира. Восстановление не реализовано.
- В отменённом турнире запрещены ввод и исправление счёта, включая старые кнопки. Его матчи остаются в истории, но целиком исключаются из общей, личной и партнёрской статистики.

### Таблицы и статистика

Два рейтинга имеют разные критерии:

| Таблица | Сортировка по приоритету |
| --- | --- |
| Зачёт одного турнира | Набранные очки ↓, разница очков ↓, победы ↓, имя по русской локали ↑ |
| Общий рейтинг | Разница очков ↓, победы ↓, имя по русской локали ↑ |

`leaderboard()` возвращает всех зарегистрированных игроков. Telegram UI исключает игроков без сыгранных матчей и показывает первые 15. Это ограничение интерфейса, а не сервиса.

Общая статистика считается по всем матчам с обоими счетами из неотменённых турниров, включая ещё незавершённые турниры:

- `gamesPlayed`, `wins`, `draws`, `losses` — число матчей и исходов.
- `tournamentsPlayed` — число турниров, где у игрока есть хотя бы один матч с результатом, а не число регистраций.
- `pointsFor`, `pointsAgainst`, `pointsDifference = pointsFor − pointsAgainst`.
- `averagePointsFor/Against = сумма / gamesPlayed`; при нуле игр — 0.
- `winRate = (wins + 0.5 × draws) / gamesPlayed × 100`; при нуле игр — 0. Ничья даёт половину победы только в формуле винрейта.
- `uniquePartners`, `uniqueOpponents` — количество различных ID в сыгранных матчах.
- `bestPartnerByWinRate` и `bestPartnerByAveragePoints` — необязательные объекты `PartnerStatistics`: `player`, `gamesPlayed`, `wins`, `draws`, `losses`, `pointsFor`, `pointsAgainst`, `winRate`, `averagePointsFor`.

Лучший партнёр по винрейту выбирается по: винрейт ↓, совместные матчи ↓, средние очки ↓, имя ↑, ID ↑. Лучший по средним очкам: средние очки ↓, совместные матчи ↓, винрейт ↓, имя ↑, ID ↑. Минимальной выборки нет — партнёр с одним матчем может стать лучшим. Если матчей нет, оба поля отсутствуют. Округление до одного знака — только отображение в боте, вычисления используют полные значения.

Особое поле `excludedFromStandingsPlayerIds` исключает результат конкретного матча для указанных игроков **только из зачёта этого турнира**. У остальных игроков результат сохраняется; общая и личная статистика исключённых игроков тоже продолжает учитывать этот матч, пока турнир не отменён. UI/сервисной операции для установки этого поля нет, но чтение и тесты поддерживают его. При интеграции нельзя потерять поле или трактовать его как отмену матча.

## Что хранится и что нужно учитывать при подключении

SQLite содержит:

| Таблица | Содержимое |
| --- | --- |
| `players` | `id`, `name`, уникальный nullable `telegram_user_id`, nullable `telegram_username`; уникальный индекс username без учёта регистра |
| `tournaments` | `id`, `payload` с полным JSON турнира, `created_at` |
| `bot_counters` | Общие счётчики, сейчас `egor_mistakes` |
| `chat_members` | Участники Telegram, ключ `(chat_id, user_id)`, JSON профиля; это не реестр игроков |
| `all_cooldowns` | Момент последнего резервирования `/all` для беседы |

Таблицы создаются конструкторами репозиториев. `migrations/0001_init.sql` описывает только игроков и турниры и не является полной схемой работающего приложения.

Игроки, турниры и статистика общие для всех чатов. `chatId`, `ownerId`, `clubId` у турнира нет. Только состояния Telegram UI изолированы по `(chatId, userId)` и живут в памяти: меню, незавершённый ввод, выбор игроков и отслеживаемые сообщения. Их не надо синхронизировать с сайтом; после перезапуска они сбрасываются.

`recognizePlayer` ищет по Telegram ID **или** username и может дописать Telegram ID в найденную запись. Это внутреннее поведение бота, а не безопасная операция входа по произвольному username. Для сайта нужен отдельно выбранный способ входа с серверной проверкой личности; клиент не может подтверждать владение профилем простым вводом `telegramUserId` или `@username`. Сейчас в сервисе нет проверки прав на создание турнира, ввод счёта или отмену.

Переименование через `renamePlayer` обновляет реестр игроков и копии имени во всех турнирах, командах и списках отдыхающих. Эти сохранения не обёрнуты в одну общую транзакцию. Привязка Telegram, напротив, обновляет реестр игроков, не все исторические копии профиля.

## Предлагаемый API v1 — ещё не реализован

Маршруты ниже — черновик для согласования, не утверждённая спецификация. Сейчас нет base URL, OpenAPI, API-ключей, HTTP-авторизации, WebSocket/SSE или вебхуков изменений. Telegram callback data — детали UI, а не API сайта.

| Метод и путь | Назначение / основа в коде |
| --- | --- |
| `GET /api/v1/players` | Список игроков, `listPlayers()`; поиск сейчас реализован в Telegram UI |
| `POST /api/v1/players` | Создание гостя по имени, `createPlayer()`; подтверждённую привязку оформлять отдельно |
| `PATCH /api/v1/players/:id` | Переименование, `renamePlayer()`; с проверкой прав |
| `GET /api/v1/players/:id/statistics` | Найти игрока, вызвать `statisticsFor(player)` |
| `GET /api/v1/leaderboard` | Общий рейтинг; явно договориться о фильтре игроков без матчей и пагинации |
| `GET /api/v1/tournaments` | История, `listTournaments()` |
| `GET /api/v1/tournaments/current` | Общая операция выбора текущего турнира, извлечённая из UI |
| `GET /api/v1/tournaments/:id` | Турнир с расписанием и результатами, `findById()` |
| `POST /api/v1/tournaments` | `{ name?, playerIds, courts, pointsPerMatch }` → разрешить ID → `create()` |
| `PUT /api/v1/tournaments/:id/matches/:matchId/score` | `{ team1Score, team2Score }` → `recordScore()` с контролем версии и прав |
| `POST /api/v1/tournaments/:id/cancel` | `cancel()` с контролем версии и прав |
| `GET /api/v1/tournaments/:id/standings` | Структурированный зачёт; вычисление сейчас встроено в текстовый `formatTournamentResults` |

Для чтения предлагаем JSON с полями описанных выше сущностей, датой ISO 8601 и отсутствующими необязательными полями. До публикации отдельно зафиксировать, какие Telegram-поля доступны клиенту; не отдавать всю запись игрока автоматически всем посетителям. Для UI можно добавить вычисляемый `status: "active" | "completed" | "cancelled"` с приоритетом отмены; сейчас такого поля нет.

При записи счёта сервер должен возвращать актуальную версию турнира. Предлагаемые ошибки: `400` — неверные данные, `401/403` — вход/права, `404` — объект не найден, `409` — устаревшая версия или отменённый турнир. Стабильный формат ошибки, например `{ "error": { "code": "TOURNAMENT_CANCELLED", "message": "Турнир отменён" } }`. Сейчас сервис бросает обычные `Error`; эти коды и HTTP-статусы нужно реализовать.

## Как получить согласованные изменения с обеих сторон

1. Одна основная база и один общий путь записи. Начальный вариант — бот и HTTP-адаптер в одном backend-процессе с общим сервисом. Отдельный процесс бота впоследствии может ходить в тот же API.
2. Вынести расчёт зачёта и выбор текущего турнира из Telegram UI в общий слой. Сайт получает готовые результаты вычислений.
3. Перенести защиту изменений из `createBot` в сервис/хранилище. Сейчас очередь по ID турнира охватывает ввод, исправление и отмену только внутри экземпляра бота. Новый HTTP-вызов её обойдёт.
4. Добавить атомарное изменение с проверкой версии (`version`/`If-Match` либо согласованный аналог). Сейчас `recordScore` читает весь JSON, меняет один матч и сохраняет весь JSON обратно. Два клиента могут затереть результаты друг друга даже при записи разных матчей. Проверка версии и сохранение должны быть одной атомарной операцией; все писатели, включая бота и переименование игрока, должны соблюдать её.
5. При конфликте вернуть `409`, перечитать турнир и показать актуальный результат. Не заменять молча более новый результат. Отмену проверять в той же защищённой операции.
6. Для повторных отправок создания турнира предусмотреть ключ идемпотентности. Сервис сейчас создаёт новый UUID на каждый вызов без переданного ID; повтор запроса может создать два турнира.
7. Для первого сайта достаточно перечитывать данные после записи, при открытии страницы и периодически во время игры. Мгновенные уведомления — отдельная функция. Уже отправленные Telegram-сообщения автоматически после изменения на сайте не обновятся; при следующем открытии бот перечитает данные, а для живого обновления потребуется механизм событий.
8. Если сайт уже ведёт свои записи, перед переключением сделать однократный импорт с явным сопоставлением ID игроков и турниров и проверкой дубликатов. Сохранять старые ID бота, результаты, отмены и исключения из зачёта. Двусторонняя синхронизация независимых баз пока не реализована.

## Что согласовать между разработчиками

- Сайт только читает данные или также создаёт турниры, вводит/исправляет счёт и отменяет турниры?
- Это один общий клуб, как сейчас, или отдельные пространства для разных групп? Второй вариант меняет схему и правила доступа.
- Кто может читать данные и кто управляет турниром? Как подтверждается Telegram-профиль и кто связывает существующих гостей?
- Где будет общий backend, какая база станет основной и есть ли уже данные сайта для импорта?
- Оставляем ли ограничения UI 1–4 корта и 16/24/32 очка? Какой максимальный размер турнира поддерживаем?
- Какая задержка обновления приемлема и нужно ли менять уже отправленные сообщения Telegram?

До ответов можно проектировать экраны и адаптер данных по текущей модели. Предложенные маршруты использовать только как моки с явной пометкой, что сервер ещё не реализован.

## Проверка совместимости перед подключением

- Созданный на сайте игрок появляется в боте с тем же ID; привязка Telegram не создаёт дубль гостя.
- Турнир, созданный любой стороной, отображается с теми же матчами, командами и отдыхающими на другой стороне.
- Счёт `20:12` при 32 очках одинаково меняет зачёт турнира, общую статистику и партнёрские показатели.
- Исправление счёта пересчитывает статистику; ничья учитывается как половина победы в винрейте.
- Отмена сохраняет историю, исключает результаты из общей статистики и запрещает старые формы/кнопки ввода.
- Одновременные изменения двух матчей не теряются; устаревшее исправление не заменяет актуальный счёт молча.
- Частичное исключение игрока из зачёта матча сохраняется и не удаляет его общую статистику.
- Переименование сохраняет ID и одинаковое имя во всех представлениях.
- 12 игроков на 2 кортах получают по 11 матчей; 11 игроков на 2 кортах — по 8 матчей и 3 отдыха.

Текущие тесты проверяют генератор, сервис, партнёрскую статистику, корректировки зачёта, отмену, Telegram UI, изоляцию сессий и `/all`. Сквозные проверки сайта/API появятся после реализации интеграции.
